# doc/incidents/ — 事故报告归档

> 与 `doc/` 根目录的**开发规约**(commit 规约、部署规约、AI 对话规约等)分开。
>
> 本目录只放**事故复盘 / 重大问题排查记录**,给将来遇到类似现象的同事/自己参考。

## 目录约定

文件名格式:`YYYY-MM-DD-<slug>.md`

- `YYYY-MM-DD` — 事故发生或排查完成的日期
- `<slug>` — 简短英文标识,描述问题

示例:`2026-08-29-ai-streaming.md`

## 写事故报告的时机

以下情况应在本目录留档:
- 跨多个模块 / 多层(后端 + 前端 + 部署)的复合问题
- 排查过程有非显然发现(pcap 数据 / 字节层证据 / 浏览器行为模拟)
- 修复后**仍可能复发**(配置容易被覆盖、依赖可能被回退)
- 团队成员可能踩同一个坑

## 报告模板建议

事故报告应包含:

1. **现象** — 用户视觉描述,不含猜测
2. **第一直觉(错的)** — 明确记录错误思路,避免下次重蹈
3. **端到端字节层 / 数据层排查清单** — 每步独立验证
4. **多层问题的拆解** — 每个问题含修复前后的对比数据
5. **教训 / 排查清单** — 给将来的自己看的 checkbox 流程
6. **关键文件清单** — 仓库 + 线上路径
7. **为什么"换协议/换方案"不能解决** — 排除常见误解

参考现有 `2026-08-29-ai-streaming.md` 的章节结构(§1-§8)。

## 与 `doc/` 根目录的关系

`doc/` 根目录放**正向规约**(应该怎么写代码、怎么部署):
- `ai-conversation.md` — AI 对话持久化数据模型
- `deploy-bt.md` — 宝塔部署备忘
- `git-commit-standards.md` — Git 提交规约

`doc/incidents/` 放**反向复盘**(出过什么问题、怎么修的、怎么避免)。
两者不重叠:规约是常态,事故是特例。
