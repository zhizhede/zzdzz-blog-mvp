# v0.4 技术方案:AI 写作工作流(语料 → 成稿)

> 范围:让用户把一段"原始语料"(想法、笔记、口述记录)整理成一篇结构完整、
> 带有作者个人文风(文笔 / 架构 / 习惯用语)的博客文章;过程中用户可以随时
> 插手——改大纲、往稿子里加料、下指令让 AI 调整——然后继续生成。
>
> 本文档面向"动手改代码的自己"。产品决策已定,不再讨论要不要做:
>
> | 决策点 | 结论 |
> | --- | --- |
> | 工作流范围 | 全三节点:提大纲 → 成稿 → 指令润色(循环) |
> | 入口 | 文章编辑器右侧 AI 面板(admin 与 space 两处编辑器共用) |
> | 用户风格 | 风格卡:自动提炼 + 可手改,存 `style_profiles` 表 |
> | 版本安全 | AI 覆盖编辑器内容前,自动存版本快照,可回滚 |
> | 形态 | **工作流,不是 agent**:流程由前端编排,后端无状态单步 action |
>
> 第一设计目标:**每一步用户都看得见、改得了、退得回去**。AI 只在被点击时
> 干活,循环的控制器是用户的手指。

---

## 0. TL;DR

- **协议**:新增一个 SSE 接口 `POST /api/v1/ai/compose`(RequireAuth),
  入参 `{action, material, outline, draft, instruction, use_own_style}`,
  action ∈ `outline | draft | refine`。一次调用 = 一次 LLM 调用,后端不存
  会话、不跑循环,SSE 事件复用 v0.3 的 `{delta}` / `{sources}` / `{error}` / `[DONE]`。
- **风格卡**:新表 `style_profiles`(按 user_id 一行),LLM 离线提炼该用户
  已发布文章的文风特征,compose 时注入 system prompt;用户可手改、可重新提炼。
- **快照**:新表 `article_versions`,采用 AI 结果前自动存一版,面板提供
  版本列表与回滚;回滚本身也先存快照,版本链永不丢内容。
- **前端**:新增共用组件 `components/WritingPanel.vue`,以右侧抽屉挂在
  `ArticleEditor.vue` 与 `space/MyNoteEditor.vue` 上,不动现有双栏布局。
- 不引任何新依赖;nginx 零改动(`/api/v1/ai/compose` 天然命中 v0.3 已配好的
  `/api/v1/ai/` 正则流式段)。

## 1. 设计原则

1. **人在环**:生成永远由用户点击触发,单步返回。后端不做任何"自己觉得
   不好再来一轮"的自主循环——那是二期 agent 化的事(见 §8 接缝)。
2. **后端无状态**:compose 接口不建会话表。工作流的"状态"就是编辑器里的
   大纲和稿子本身,由前端持有并回传。少一张表,少一类一致性问题。
3. **覆盖必留痕**:AI 结果进编辑器之前,当前内容必须已成快照。快照失败
   则阻断采用。信任是写作工具的第一约束。
4. **降级一致**:embedding 未配置 / 风格卡缺失 / LLM 失败,都要落到明确的
   提示,不允许静默用错风格或吞掉错误。
5. 不破坏 v0.2 既定原则:单 Postgres、不引新依赖、改动面最小。

## 3. 数据库变更

`migrations/0010_writing_workflow.sql`,幂等,可重跑。

```sql
-- 风格卡:每个用户一行
CREATE TABLE IF NOT EXISTS style_profiles (
    user_id    BIGINT PRIMARY KEY,          -- REFERENCES users(id)
    profile    TEXT NOT NULL,               -- LLM 提炼的文风描述(markdown)
    source     VARCHAR(16) NOT NULL DEFAULT 'auto',  -- auto | manual
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 文章版本快照:AI 采用前 / 回滚前自动写入
CREATE TABLE IF NOT EXISTS article_versions (
    id         BIGSERIAL PRIMARY KEY,
    article_id BIGINT NOT NULL,             -- REFERENCES articles(id) ON DELETE CASCADE
    title      TEXT NOT NULL DEFAULT '',
    summary    TEXT NOT NULL DEFAULT '',
    content    TEXT NOT NULL,
    origin     VARCHAR(16) NOT NULL,        -- manual | ai_outline | ai_draft | ai_refine | pre_restore
    note       TEXT NOT NULL DEFAULT '',    -- 本次采用的 instruction / 加料摘要(截 500)
    created_by BIGINT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_article_versions_article
    ON article_versions (article_id, created_at DESC);
```

- 保留策略:每次 insert 后 prune,每篇文章只留最近 50 版(写死,后文书量大再进配置)。
- `origin` 里 `manual` 留给前端"手动存个版本"按钮(二期),首版只有 AI 链路与 `pre_restore`。

## 4. 后端:compose 接口与 WritingService

### 4.1 路由

```
POST /api/v1/ai/compose                   RequireAuth, SSE
GET  /api/v1/writing/style-profile        RequireAuth
PUT  /api/v1/writing/style-profile        RequireAuth   (手改, source=manual)
POST /api/v1/writing/style-profile/derive RequireAuth   (重新提炼, 同步)
GET  /api/v1/articles/:id/versions        RequireAuth
POST /api/v1/articles/:id/versions        RequireAuth   (存快照, 采用前调)
POST /api/v1/articles/:id/versions/:vid/restore  RequireAuth
```

新文件 `handler/writing.go` + `service/writing.go`;AI 会话体系(`ai_conversations`)
完全不复用——写作流不是聊天,别混。

### 4.2 compose 请求/响应契约

```jsonc
// 请求
{
  "action": "outline | draft | refine",
  "material": "原始语料(必填, outline/draft 必带; refine 可不带)",
  "outline": "当前大纲(draft/refine 时带)",
  "draft": "当前稿(refine 时必带)",
  "instruction": "用户本次的额外指令(可空)",
  "use_own_style": true
}
```

响应流(复用既有 SSE 格式):

```
data: {"delta": "..."}                       // 正文增量
data: {"sources": [{"title": "...", "id": 1}]}   // 风格样例来源(用了哪几篇文章提炼/示范)
data: {"error": {"code": 1, "message": "..."}}
data: [DONE]
```

handler 侧组装 prompt → 调既有 `service/ai.go` 的 LLM 客户端流式接口 →
逐 delta 写回,与 `SendMessage` 同一套写法。

### 4.3 Prompt 契约(本方案的核心资产)

**system**(三段拼装):

1. 角色:"你是博客写作助手,把用户的原始语料整理成一篇博客文章。"
2. 风格卡(`use_own_style=true` 且查到 profile 时):"作者的文风如下,严格遵守:
   {profile}";查不到时替换为通用文风描述,并通过 SSE `meta` 提示前端降级。
3. 输出契约,按 action 分支:
   - `outline`:只输出 markdown 无序列表,每行一个要点,不超过 12 行,不解释。
   - `draft`:只输出 markdown 正文,不要标题前后的寒暄,禁止用代码围栏包裹全文。
   - `refine`:返回修改后的**全文**(不是 diff、不是片段),保持未提及部分原样。

**user**:`<语料>...</语料>` / `<当前大纲>...</当前大纲>` / `<当前稿件>...</当前稿件>` /
`<本次要求>...</本次要求>` 各段有则拼,空段跳过。

**陷阱与对策**:模型爱把全文包 ` ```markdown ` 围栏——后端对 draft/refine 输出
剥壳(剥首尾 fence)再下发。温度按 action 写死:outline 0.4 / draft 0.7 / refine 0.5。

### 4.4 校验与边界

- `material` 上限 2 万字,超出 400;`draft` 上限 5 万字。
- 所有 compose 接口 RequireAuth;语料是用户输入,**不落库**(只随请求进出),
  避免素材库的存储与隐私包袱(未来要存,见 §8)。
- LLM 失败/超时:推 `data: {"error": ...}` 后 `[DONE]`,前端把按钮恢复可点。

## 5. 风格卡:提炼与注入

### 5.1 抽样策略(一个反直觉的决策)

风格样本**不用向量召回,直接查表**:取该用户 `articles` 中
`author_id = 自己 AND visibility IN ('public','private')`(排除 draft——
未完成语料会污染提炼)按 `created_at DESC` 取 5 篇,每篇截前 1500 字。

理由:风格是"怎么写",不是"写什么",语义检索按主题相似度选样本,反而
会把样本偏置到某个题材上;"最近 5 篇"对文风的代表性足够且零成本。
v0.3 的 RecallService 在此只借用其**判权思路**,不调用其检索。

### 5.2 提炼

`WritingService.DeriveStyleProfile(userID)`:抽样 → 单次 LLM 调用,输出
结构化 markdown 风格卡(固定小节:语气与视角 / 句式与长短 / 习惯用语与口头禅 /
文章结构套路 / 标点与格式偏好 / 禁用与雷区)→ upsert `style_profiles`,
`source='auto'`。

- 触发:面板首次打开且无风格卡时自动提炼一次(前端提示"正在学习你的文风");
  之后仅手动点"重新提炼"。文章更新不自动重提(成本与抖动),面板展示
  `updated_at` 让用户自己判断新旧。
- 用户手改:`PUT /writing/style-profile`,`source='manual'`;再次"重新提炼"
  会覆盖手改内容,确认弹窗提示。
- 从未发过文章的用户:提炼返回空样本错误,前端引导手写风格描述。

### 5.3 注入

compose 时按 §4.3 拼 system。风格卡上限 2000 字(提炼时就控制),超长截断。

## 6. 版本快照与回滚

### 6.1 采用流程(前端两步,快照失败即阻断)

```
[面板预览 AI 结果] --点击"采用"-->
  ① POST /articles/:id/versions {origin, note}   // 服务端读当前文章存快照
  ② 快照成功 → 替换编辑器 content/title/summary → 走既有保存链路
```

`note` 记录本次 action 与 instruction 摘要,版本列表里展示"这版是怎么来的"。

### 6.2 新建未落库文章的空档

autosave 与版本表都依赖 article id。文章还没有 id 时:AI 结果仅保留在
**面板的内存生成历史**(最近 10 条,可回填预览),不做服务端快照;编辑器
顶部提示"先保存文章,才能获得版本快照"。这是有意接受的限制,不为它造
临时 key 机制(见 §8:素材库是更正确的长期解法)。

### 6.3 回滚

`POST /articles/:id/versions/:vid/restore`:服务端先把**当前内容**存一条
`origin='pre_restore'` 快照,再把目标版本写回文章。版本链只增不改,
任何操作都可再退回。

## 8. 与未来演进的接缝(只允许填空,不允许返工)

| 未来可能变 | 现在的做法 | 未来只允许"填空"的方式 |
| --- | --- | --- |
| 工作流 agent 化(自动多步) | compose 是无状态单步 action,action 为开放枚举 | 服务端加编排器组合既有 action,协议不动 |
| 素材库(语料入库、复用) | 语料只存在于请求体 | 新建 materials 表,compose 入参加 `material_id`,老字段保留 |
| 按节点换模型 | 复用 `ai.*` 单一配置 | 配置加 `ai.writing.overrides`,按 action 覆盖 |
| 风格抽样升级(代表性/向量) | 最近 5 篇查表 | 只换 `DeriveStyleProfile` 内部,入参出参不变 |
| 手动版本/对比视图 | versions 表已有 origin/manual 预留 | 直接消费表,无迁移 |

## 10. 风险与对策

| 风险 | 对策 |
| --- | --- |
| refine 输入 = 全文 + 语料 + 风格卡,token 大 | 字数硬上限(§4.4);MiniMax 长上下文可承受;首版不做分段润色 |
| 风格卡把文风学"僵" | 风格卡可手改是第一出口;instruction 每次可覆盖("这次口语一点") |
| AI 覆盖丢稿 | 快照失败阻断采用(§6.1);无 id 文章靠面板内存历史兜底并提示 |
| autosave 与采用写入竞争 | 采用后主动触发一次保存,编辑器自身已有未保存离开守卫(0901) |
| SSE 过 nginx | `/api/v1/ai/compose` 命中已配好的 `/api/v1/ai/` 正则流式段,零改动 |
| 提炼接口被刷(同步 LLM 调用) | 前端按钮防抖 + 后端每 user 每分钟限 1 次提炼(内存计数即可) |
