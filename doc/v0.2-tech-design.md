# v0.2 技术方案:草稿自动保存 + 标签系统

> 范围:实现 [`doc/product-design.md`](./product-design.md) 中 v0.2 的两项产出
> —— 草稿自动保存(优先)、标签系统(已在 `web/demo/` 原型)。
>
> 本文档面向"动手改代码的自己",不写运营文案。

---

## 0. TL;DR

- **草稿自动保存**:在 `articles` 表复用 `visibility='draft'`,新增接口
  `PUT /api/v1/articles/:id/autosave` + 编辑器端 8s 防抖 + `localStorage` 离线兜底。
- **标签系统**:新增三张表 `tags` / `article_tags` / 复用 `articles.id`,
  新增标签 CRUD(由 admin 管)+ 文章提交时一并 `replace` 关联。
- 不改架构(单 SPA + Gin + Gorm + Postgres),不引新依赖,不破坏现有 `visibility` 语义。

## 1. 草稿自动保存

### 1.1 现状(为什么"自动保存"不是白送的)

| 现状 | 影响 |
| --- | --- |
| `articles` 表没有"软删/未发布"区分,只有 `visibility='draft'` | 不能简单复用,得想清楚 draft 怎么从列表里出去 |
| `PUT /articles/:id` 是"保存"语义,会更新 `updated_at` | 草稿频繁落库会让 `updated_at` 抖动,影响列表排序 |
| 编辑器关闭浏览器=内容丢失 | 没有客户端兜底 |

### 1.2 设计目标

- **写 5 分钟不掉字**:网络断 / 浏览器关 / 服务挂了,内容不丢
- **不打草稿债**:存进数据库的草稿数量要有上限,旧的能自动清
- **不打扰**:作者只关心"我刚才那行没丢吗?",不弹通知轰炸

### 1.3 存储形态:复用 `articles` 表 + `draft` 可见性

**不**新建 `article_drafts` 表。理由:

- `draft` 已经是"对 URL 404"的语义,正好和"自动保存的脏数据"语义一致
- 复用 model / handler 框架,改动面最小
- 草稿也参与 `author_id` 隔离,权限逻辑零差异

**但**要解决"频繁 autosave 把 updated_at 弄花"的问题:
- 新增字段 `last_autosaved_at *time.Time`,**只**在 autosave 接口里改
- `articles.updated_at` 仍由"主动保存/发布"动
- 列表查询默认按 `updated_at DESC` 排序,语义不变

### 1.4 数据库变更

文件 `server/migrations/0007_article_autosave.sql`:

```sql
-- 自动保存时间戳, 与 updated_at 区分, 不影响列表排序
ALTER TABLE articles
  ADD COLUMN last_autosaved_at TIMESTAMPTZ;

-- 草稿清理: 30 天没动过的 draft 自动删 (后台 cron)
-- 索引让 "找过期草稿" 走索引, 不全表扫
CREATE INDEX idx_articles_draft_autosaved
  ON articles (last_autosaved_at)
  WHERE visibility = 'draft';
```

### 1.5 API

| Method | Path | 鉴权 | 行为 |
| --- | --- | --- | --- |
| `PUT` | `/api/v1/articles/:id/autosave` | 登录 (作者本人 / admin) | 只改 4 个字段:`title` / `summary` / `content` / `category_id`;`visibility` 保持 `draft`;写 `last_autosaved_at` |
| `GET`  | `/api/v1/articles/autosave/drafts` | 登录 | 列"我自己的 draft",按 `last_autosaved_at DESC`,带分页 |
| `DELETE` | `/api/v1/articles/:id` 已有 | 同 | 真删草稿 |

请求体(只接白名单字段):

```json
{
  "title": "...",
  "summary": "...",
  "content": "...",
  "category_id": 1
}
```

响应:

```json
{
  "code": 0,
  "data": {
    "id": 42,
    "last_autosaved_at": "2026-04-12T10:33:21Z",
    "server_received_at": "2026-04-12T10:33:21Z"
  }
}
```

### 1.6 前后端契约

- **触发**:编辑器内容变化时,**8 秒防抖**(打字慢的人不会被打断,打字快的人不会发洪水)
- **顺序**:先写 `localStorage`(`draft:<articleId>`)→ 再发请求 → 成功后用 `last_autosaved_at` 更新顶栏状态
- **离线兜底**:请求失败时把"待同步标记"写进 `localStorage`;下次进入页面 / 30s 间隔内 retry
- **可见性**:新建按钮 (`/admin/articles/new` / `/space/notes/new`) 直接走 `POST /articles` 且 `visibility=draft`;返回的 id 立刻挂到 URL,后续所有 autosave 都基于这个 id

### 1.7 草稿清理(简单实现,不引 cron 框架)

- 新增 `server/cmd/draft-cleanup/main.go`(可执行子命令,放 Makefile 里)
- 一行 SQL:`DELETE FROM articles WHERE visibility='draft' AND (last_autosaved_at IS NULL OR last_autosaved_at < now() - interval '30 days') RETURNING id;`
- 部署侧挂系统 cron / k8s CronJob,每天 04:00 跑

### 1.8 不做

- ❌ 多端同步(冲突合并):先单设备,够用就行
- ❌ 协作锁:单人产品,不需要
- ❌ 历史版本:有 git 兜底,不另存
- ❌ autosave 失败重试队列(指数退避):localStorage 标记 + 简单 retry 就够

## 2. 标签系统

### 2.1 数据模型

文件 `server/migrations/0008_tags.sql`:

```sql
CREATE TABLE tags (
  id BIGSERIAL PRIMARY KEY,
  name VARCHAR(64) NOT NULL UNIQUE,
  slug VARCHAR(64) NOT NULL UNIQUE,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE article_tags (
  article_id BIGINT NOT NULL REFERENCES articles(id) ON DELETE CASCADE,
  tag_id     BIGINT NOT NULL REFERENCES tags(id)     ON DELETE CASCADE,
  PRIMARY KEY (article_id, tag_id)
);

CREATE INDEX idx_article_tags_tag ON article_tags (tag_id);
```

中间表 + 复合主键,不存顺序(标签是无序集合)。

### 2.2 仓库层(轻量,先不引 sqlc)

`server/internal/model/model.go` 新增:

```go
type Tag struct {
  Base
  Name string `gorm:"size:64;uniqueIndex;not null" json:"name"`
  Slug string `gorm:"size:64;uniqueIndex"        json:"slug"`
}
func (Tag) TableName() string { return "tags" }
```

Article 不加 GORM 关联字段(避免预加载搞复杂),`service` 层用裸 SQL 维护 `article_tags`。

### 2.3 API

| Method | Path | 鉴权 | 说明 |
| --- | --- | --- | --- |
| `GET`    | `/api/v1/tags` | 公开 | 列表 + 每标签的公开文章数(为首页云服务) |
| `POST`   | `/api/v1/tags` | admin | 新建(name 必填,slug 留空自动从 name 生成) |
| `PUT`    | `/api/v1/tags/:id` | admin | 改名(注意:关联文章不动) |
| `DELETE` | `/api/v1/tags/:id` | admin | 删标签 + 联级删 `article_tags` 行 |
| 文章接口 | 改 `POST/PUT /articles` | 已有的 | 请求体加 `tag_ids: number[]`,服务端 `replace` 该文章的全部标签 |

### 2.4 查询改动(影响小,只 1 处)

`GET /articles?tag_id=42` 新增 query 参数:

```sql
-- 伪 SQL
SELECT a.* FROM articles a
JOIN article_tags at ON at.article_id = a.id
WHERE at.tag_id = $1 AND a.visibility = 'public'
ORDER BY a.created_at DESC;
```

- 现有 `category_id` / `q` / `author_id` 过滤器**不变**
- 多标签过滤 (`?tag_ids=1,2,3`) v0.2 **不**做(先单标签)
- 公开/可见性逻辑保持现状

### 2.5 前端

- `web/src/api/index.ts` 加 `tagApi`(list/create/update/remove)
- `web/src/views/admin/ArticleEditor.vue` 已 demo 过,挪过来即可:多选 pill 区域 + 校验
- `web/src/views/public/Home.vue`:顶部 `TagCloud` 组件、按 `tag_id` 过滤
- `web/src/views/public/ArticleDetail.vue`:meta 行加标签 chips,点回 `/?tag_id=...`

### 2.6 已有数据迁移

老文章没标签。**不做 backfill**——种子数据可以手动补一两个,真实老数据用户自己挑要不要打。脚本 `0008` 只动 schema,不动内容。

## 4. 验证清单(手测,不是 CI)

### 草稿自动保存

1. 写 5 分钟,关闭浏览器,再打开同一 URL → 草稿还在(从 localStorage 恢复)
2. 拔网线,写一行 → 顶栏显示"未同步";恢复网线 → 自动 retry 成功
3. 一篇文章连续 autosave 50 次 → 数据库 `last_autosaved_at` 一路更新,`updated_at` 不变
4. 30 天前的 draft 在清理任务跑完后从列表消失(手测可以改阈值到 1 分钟)

### 标签

1. admin 在后台新建标签 `Go` / `Vue` / `LLM`
2. 编辑文章勾三个标签 → 公开页能看到 chips
3. 改文章时取消 `LLM` → `LLM` 计数 -1,文章 meta 不再显示
4. 删 `Vue` 标签 → 所有带 Vue 的文章自动不再带这个 tag(级联)
5. 公开页 `/?tag_id=<id>` 只显示该标签下文章

### 权限

1. reader 调 `PUT /articles/:id/autosave`,id 是 admin 的 → 403
2. reader 调 `POST /tags` → 403
3. reader 进 `/admin/categories` 路径 → 已被 router 拦截,接口层不需要再加守卫

## 5. 风险与回滚

| 风险 | 缓解 |
| --- | --- |
| autosave 把数据库写爆 | 防抖 8s + 单设备 1 篇文章最多 1 个 in-flight |
| 标签删了文章信息丢失 | 级联删,先和作者确认;UI 上删标签要二次确认 + 列出受影响文章数 |
| 草稿清理删错 | WHERE 加 `visibility='draft'`,只删草稿;发布过的不受影响 |
| migration 失败 | 0007 / 0008 都是加列 / 加表,GORM 不读新字段不报错,可单独回滚 |
| 兼容旧前端 | 老前端不调新接口,完全兼容;`tag_ids` 字段为 optional |

回滚按 migration 文件逆序执行即可,代码侧用 git revert。

## 7. 不属于 v0.2(留给 v0.3+)

- 多标签过滤(`?tag_ids=1,2,3`,AND / OR 语义)
- 标签合并(把 `postgres` 合并到 `PostgreSQL`)
- 标签页(`/tag/:slug` 单独的归档页)
- 标签自动补全(打字时联想已有标签)
- autosave 历史快照(只保留最新一版)
- 协作锁 / 多端冲突合并
